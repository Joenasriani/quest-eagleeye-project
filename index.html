Meta Quest to EagleEye: Tactical XR Concept Study

Date: December 10, 2025
Location: Lebanon
Type: Concept study

Evidence status: Research for a proposed mixed-reality prototype, including system architecture and a test plan. It does not provide records establishing a completed integrated build or measured performance. Component compatibility, latency, range and runtime require validation. No functional equivalence with military systems is claimed.

Abstract

Project EagleEye explores a wearable mixed-reality interface combining consumer hardware, thermal sensing and off-grid communications. This study outlines a proposed architecture, component budget and integration questions. The assembly descriptions and code snippets are design material, not evidence of a validated system.

1. Introduction

1.1 Background

The design considers how geospatial information and thermal imagery could be displayed through a consumer mixed-reality headset. Integrating sensing, communications, power and display introduces compatibility and calibration questions that must be tested.

1.2 Objective

The objective is to investigate whether thermal data and location information can be presented in a wearable interface for search-and-rescue research and off-grid coordination. Suitability for operational use has not been established here.

2. System Architecture

The proposed architecture has four primary subsystems:

  1. Visual Compute: Meta Quest 3 (Android-based VR/MR headset).
  2. Communications: Heltec V3 (LoRa mesh radio; no built-in GNSS receiver, so reported node position needs an external coordinate source).
  3. Sensor: Topdon TC001 (LWIR Thermal Camera).
  4. Proposed Software: ATAK-CIV as an optional external data source and a proposed Unity/Android application layer; no interoperable bridge or custom operating system is demonstrated.

3. Proposed Hardware Integration

3.1 Component Selection

  • Meta Quest 3: Selected for color passthrough and spatial tracking as a candidate for overlays. Meta's Passthrough Camera API accesses supported headset RGB cameras under version and permission constraints; it does not establish external USB thermal-camera access. Depth and head pose do not replace thermal calibration. Alignment, latency and comfort require evaluation.
  • Heltec WiFi LoRa 32 (V3): An ESP32-S3/SX1262 LoRa board with compatible Meshtastic firmware. Applicable frequencies, firmware and local regulatory constraints require checking for the actual hardware and location. It can participate in an off-grid mesh network; this board has no built-in GNSS receiver. Position transmissions depend on coordinates provided by a compatible external receiver or paired device. Frequency selection must comply with local radio regulations.
  • Topdon TC001: A USB-C thermal camera marketed for supported host devices, with a manufacturer-specified 256 × 192 infrared sensor and nominal 25 Hz frame rate. Its USB interface, decoder, SDK licensing and compatibility with Quest Horizon OS are unverified.

3.2 Power and Data Topology

A critical engineering challenge is the Meta Quest 3’s single USB-C port. The system requires simultaneous power delivery (charging) and data ingestion (thermal camera). Passive splitters are insufficient.

Proposed option: An active USB-C Hub with Power Delivery (PD) Pass-Through might provide charging and peripheral access, but PD passthrough alone does not establish Quest USB host operation, sufficient peripheral power or driver compatibility. An external compatible Android capture device streaming to Quest over a local network is a separate, untested fallback.

3.3 Proposed Assembly

The proposed mounting layout distributes components between the front and rear of a helmet. Comfort, balance and safe mounting require physical evaluation.

  • Front: Headset and Thermal Camera (mounted via 3M Dual Lock tape).
  • Rear: Battery and USB Hub (mounted via heavy-duty Velcro to the nape).
  • Spine: Cables routed along the top helmet strap with strain-relief loops to prevent port damage.

4. Software Environment

Implementation status: The following snippets are historical nonfunctional illustrations, not build-ready examples. They do not establish camera compatibility, USB access, a working thermal overlay or a complete application. The WebCamTexture device-name matching sample is not a TC001 driver or decoder.

The proposed software architecture has two experimental pathways: Android-side data acquisition or bridging, and Unity/OpenXR-based visualization. Sideloading ATAK-CIV does not establish interoperability with a Unity application. Quest 3 has no native eye-tracking hardware; head-directed rays, hand tracking or controller pointing are distinct alternatives.

4.1 Android Manifest Override

Objective: declare USB host support. The application must separately discover the peripheral and obtain device-access permission through Android's USB APIs. This manifest alone does not enable camera access; actual USB enumeration, permissions, USB interface/endpoint protocol, decoding and power topology must be separately validated.

Assets/Plugins/Android/AndroidManifest.xml 
<manifest xmlns:android="http://schemas.android.com/apk/res/android" package="com.EagleEye.Research">
    <!-- Declare USB host feature -->
    <uses-feature android:name="android.hardware.usb.host" />
    <uses-permission android:name="android.permission.CAMERA" />
    
    <application android:label="EagleEye OS" android:theme="@android:style/Theme.Black.NoTitleBar.Fullscreen">
        <activity android:name="com.unity3d.player.UnityPlayerActivity" android:launchMode="singleTask">

                <action android:name="android.intent.action.MAIN" />

4.2 Unity C# Script: Thermal Overlay

Historical illustrative texture-display code only, not a tested or recommended thermal acquisition interface. USB host declarations and camera permissions do not make a TC001 available through Unity WebCamTexture; vendor-specific capture, permissions and frame decoding must be verified. The example produces a headset-fixed image, not a calibrated world-registered thermal overlay. Matching a USB device name in WebCamTexture.devices cannot establish direct TC001 capture; use a separately proven host or gateway in the first experiment.

Assets/Scripts/ThermalOverlay.cs 
using UnityEngine;
using UnityEngine.UI;

public class ThermalOverlay : MonoBehaviour {
    public RawImage overlayDisplay;
    private WebCamTexture thermalCam;

    void Start() {
        // Iterate through devices to find the Topdon/USB Camera
        foreach (var device in WebCamTexture.devices) {
            if (device.name.Contains("USB") || device.name.Contains("Topdon")) {
                thermalCam = new WebCamTexture(device.name, 256, 192, 25);
                overlayDisplay.texture = thermalCam;
                thermalCam.Play();
            }
        }
    }
}

5. Proposed Testing and Evidence Requirements

Testing must independently establish USB descriptors, host permission and real TC001 frame decoding; capture-to-display latency; calibrated intrinsics, mounting extrinsics and time-matched pose; multi-depth registration error; GNSS source, packet age and loss, WGS84-to-local conversion; sustained USB data with charging, thermal load, and interaction performance. Displaying a thermal image on a floating panel is not evidence of spatial registration.

Latency and runtime are not established. Measurements require an integrated prototype, a defined test method and recorded results.

Any future results should identify the hardware and software versions, test conditions, measurement method and underlying records.

7. Conclusion

EagleEye documents a proposed approach to combining consumer mixed-reality hardware with sensing and communications. Feasibility and performance remain to be established through documented integration and testing.

7.1 Future Work

Next steps are to verify component compatibility, document an integrated prototype and publish reproducible measurements before making performance claims.
